# 性能与可靠性改动说明

本次工作基于 `https://github.com/antioblivionis/MiRearScreenSwitcher.git`，基线提交 `7e0ae1a35aea58c1f94019cf3cb54681adb54b9d`。修改保留在本地工作区，没有提交、推送或发布。包名、URI 协议和主要功能入口保留。

## 已修改的关键路径

| 路径 | 原问题 | 当前实现 |
| --- | --- | --- |
| 背屏任务监控 | 周期 shell 查询、持续干预 Launcher；查询异常容易被当成退出 | UserService 注册任务栈回调，150 ms 合并事件；精确比较包名和任务 ID；连续两次已知不匹配才结束会话。查询失败保留会话。注册事件失败时才使用 15 秒查询回退。连续事件不能无限推迟已排定检查。 |
| Launcher | 持续查进程、反复 force-stop | 删除守护式击杀。显式切换时，仅当前背屏前台确实是 `com.xiaomi.subscreencenter` 才允许一次 force-stop，并限制短时间重复执行。恢复前先检查背屏前台，避免旧动画覆盖新应用。 |
| 任务移动 | 硬编码 Binder transaction 编号，文本模糊匹配任务/屏幕 | 在 Shizuku UserService 内使用运行系统的 `IActivityTaskManager` Stub 和方法签名；移动后再次核对任务、包名与显示器。一个 root 含多个任务或不能可靠识别时拒绝移动，避免连带移动其他应用。 |
| 常亮 | 多组件各自每 100 ms 执行唤醒 shell；亮屏 WakeLock 范围不精确 | 共享 `RearWakeController`，按实际 display 状态和使用者租约发唤醒请求，优先直接注入输入；失败时才单次 shell 回退。亮屏状态的 15 秒补查不执行唤醒命令。关闭常亮或最后使用者退出后注销监听和连接。 |
| Shizuku 连接 | 各组件独立绑定、解绑时销毁其他使用者的服务；高频重连 | 全应用共享 UserService 及连接所有权；迟到连接不能覆盖新尝试；断线/权限事件驱动，有限次数退避；最后使用者退出才销毁。录屏、URI 等待连接用信号和超时，取消每 100 ms 等待循环。 |
| 动画启动/结束 | 主线程反复启动和查询任务；通知文本拼 shell；旧 Activity 销毁影响新动画 | 共用串行启动线程，类型化参数、安全 shell 引用、`am start -W` 与实际组件核对；通知页保留一次主屏启动后移动的 OEM 回退，充电页只允许直接启动到背屏。动画使用会话编号，旧结束回调不能结束新会话；同实例收到新 Intent 会刷新内容。拔电清除待恢复的充电会话。 |
| 录屏 | 全局 PID 文件、按进程名找录屏器、固定延迟后宣称保存 | 持有本次启动的 Process、PID、唯一文件路径和回调；只停止本次录屏，发送 SIGINT 等待正常结束。退出码、非空文件及可读取的视频时长通过后才报告保存。连接丢失显示“状态未知”。 |
| 截图与 URI | 即使失败/异常也提示已保存；移动失败仍结束监控 | 截图命令退出且文件非空才报告成功；所有截图入口尊重结果。URI 拉回失败不提示成功，也不停止现有监控。启动目标应用不再先杀当前应用或目标应用。 |
| 子进程 | 输出阻塞、无上限等待、错误输出当成功 | `CommandRunner` 同时排空合并后的 stdout/stderr、限制 256 KiB 输出、限时等待、回收进程并保留中断状态。截断和非零退出均不视为成功。 |
| UI 与显示信息 | 异步返回更新已销毁 Flutter 页面；错误显示缓存永久生效；主线程等待 DPI | 页面销毁后不继续 DPI/旋转请求，不接受过期回调；优先读 DisplayManager 当前尺寸与 DPI，失败缓存可重试；图标限制解码尺寸；release 不打印 Flutter 调试日志。 |

删除了没有调用者且依赖跨进程静态变量的旧广播接收器、引用不存在类的 Vulkan 布局；补齐磁贴 API 版本判断、内部广播非导出注册和包名限定。保留通知应用白名单所需的全部包可见性权限，并仅对这一项 Lint 检查记录了有原因的局部例外，没有通过整体关闭 Lint 规避错误。原有 `Instantiatable` 排除项保留。

## 实际限制和兼容边界

- Shizuku 的 ADB 模式仍是 shell 权限。UserService 可以使用隐藏 API，不等于得到 root 或绕过 HyperOS 的窗口、任务和锁屏策略。运行时反射调用被 ROM 拒绝时，查询可回退到 shell；任务移动不会猜测另一个 Binder 编号。
- 应用原有背屏操作仍以逻辑 display 1 为目标，未扩展成通用多显示器管理器。截图/录屏会把它映射到 dumpsys viewport 的真实物理 ID；缺失、虚拟显示或歧义映射直接失败，不默认使用第二块物理屏或 ID 1。
- 多任务 organized root 暂不支持单任务跨屏移动。安全拒绝可能减少部分分屏场景的可用性，这是明确的取舍。
- 如果 OEM 允许注册任务事件却漏发事件，单靠“注册成功”无法证明每次切换都能观测；此项要通过目标 ROM 的任务切换验收。唤醒的 15 秒补查也无法保证某些 ROM 上绝不短暂熄屏。
- 官方 Launcher 的包名/组件沿用目标机型约定。一次性 force-stop 有实际副作用；系统可能重新拉起它。本次没有通过禁用整个系统包、永久修改系统设置或周期击杀来掩盖这个限制。
- `screenrecord` 目前显式限制单次 180 秒、20 Mbps。使用 SIGINT 等其正常封装文件；Shizuku 崩溃、系统强杀或设备关机不保证文件可恢复。进程停止基于所拥有 Process 的存活检查和 PID，没有宣称具备 pidfd 级的原子进程身份保证。连接中断后不会把未知结果显示成已保存，也不会扫描并清杀其他录屏进程。
- 截图成功代表命令与文件检查通过，不保证唤醒后的第一帧一定已经刷新。媒体扫描失败也可能造成有效文件尚未立即出现在相册，需要实机核对。
- 原有动画绘制实现、所有通知/锁屏组合、所有厂商 ROM 并未全面重写或实测。自动化测试覆盖解析、命令运行器和部分生命周期，不等价于 Android Binder 或真实屏幕测试。

## 充电动画背屏稳定性（2026-11-11）

在 Xiaomi 2509FPN0BC、Android 17 / HyperOS 4.0 上复现了充电动画被打断的问题。旧包的设备日志显示：充电页启动前停止背屏中心；系统随后重启背屏中心，约 4 秒后其 `SubScreenRestartDozeListener` 请求背屏进入休眠，背屏中心重新到前台。用户观察到动画很难出现、需要触摸或很快退回。

本次只修改 `ChargingService`：启动充电页时不再停止背屏中心，直接唤醒并启动原有页面。其他入口的背屏中心处理、液体外观和充电时间设置未改动。使用相同调试证书覆盖安装后，在同一设备上：用户确认常亮开启时动画出现并保持；关闭常亮后动画出现并在约 8 秒后关闭。日志记录关闭常亮时，页面于 23:04:26.478 启动、23:04:34.584 销毁；常亮测试中充电页持续到关闭常亮设置。

该结论针对这次实测场景，不能推断其他小米机型、所有息屏状态或 Shizuku 断连时的表现。确认过的独立限制仍在：插电时任务服务未连接不会补播；拔电时会话提前结束可能跳过页面的恢复分支。它们没有包含在这次单项修改中。

## 充电常亮时双击（2026-11-11）

同一台 HyperOS 4.0 设备的实测显示：双击充电页面后，系统以 `sleep_button` 原因让背屏进入休眠，并把背屏中心移到前台；充电 Activity 此时仍在后台，并非它主动关闭。原来的常亮控制器只能重新请求点亮屏幕，不会把该 Activity 移回前台。

充电常亮页面现在识别发生在本页面的双击，在系统切换后尝试恢复当前充电页。恢复前检查充电状态、常亮开关、当前动画会话、页面实例、短时有效期和背屏中心前台身份；如果检查时发现通知、其他前台任务或失效会话，就跳过恢复。前台检查与启动不是系统级原子操作，仍存在极短的并发窗口。每次手势最多两次短时检查，成功后不再重复，不修改系统手势设置，也不停止背屏中心。由于系统仍先处理休眠，可能短暂看到背屏中心；不能保证完全消除闪动。

设备实测连续四次双击均返回充电页，用户确认闪出背屏中心的时间非常短。日志中背屏中心置前到再次发起充电 Activity 分别约 68–73 毫秒；这不是屏幕实际视觉延迟的精确测量。随后拔电，充电页正常销毁；未单独实测通知与手势同时发生的竞态或其他机型。

## 背屏常亮、遮盖和本地发行包（2026-11-12）

`3.3.0+2010` 修复两个常亮模式和背屏遮盖检测。设备将背部接近传感器作为小米自定义类型暴露，原来只枚举标准接近传感器而漏掉它；现在枚举所有传感器，只选择明确标识背部、以变化事件上报的接近传感器，并优先使用唤醒型。用户在实机遮盖后确认投放应用返回主屏，日志记录检测值从 5.0 变为 0.0，遮盖防抖后释放了背屏亮屏锁。

两种常亮模式共用背屏专用亮屏锁，只在确认主屏和背屏属于不同电源组时申请。锁随使用者和远程服务生命周期释放；系统显式让背屏休眠后，根据休眠事件查询背屏电源状态并重新唤醒。充电动画仍使用原有唤醒租约。移除普通投放前对背屏中心的强行停止，以避免 HyperOS 重启背屏中心并使背屏休眠。用户确认未投放应用时，双击背屏和锁主屏后都能很快恢复；其他机型、电源组不独立的设备和权限受限的系统尚未验证，不会改用影响所有屏幕的亮屏锁。

在移除投放前强停背屏中心之前，实机已确认投放应用时亮屏锁位于背屏电源组，并确认遮盖后返回主屏。移除该强停调用后，普通投放的完整静置复测尚未收到用户结果。

发布构建可通过 Gradle 属性 `sharedReleaseSigningScript` 指向外部签名脚本；密钥及口令不进入仓库。用户指定的发布证书与 GitHub V3.2.0 的证书不同，因此用该密钥签署的 APK 无法覆盖安装原发行包，也无法覆盖本轮调试签名验证包。旧发行包的内部版本号为 2009，新包为 2010；版本号高低不能消除签名不一致的限制。

## 背屏录屏启动与静止画面时长（2026-11-12）

这台 HyperOS 4.0 设备的 `dumpsys display` 输出约 379 KB，超过命令执行器 256 KiB 的完整输出上限，原来的物理屏幕编号查询因此失败，录屏器尚未启动。现在只读取显示管理器的 viewport 列表，仍要求命令成功、输出不截断且逻辑背屏能唯一映射到物理屏幕。背屏截图也使用同一映射。设备上直接验证背屏录制生成了视频，随后用户确认应用中的录制可以启动。

实测还发现静止背屏录制约 5 秒后，视频文件只有约 0.27 秒，而持续变化画面的录制时长正常。系统录屏器在静止尾段没有延长最后一个样本。现在仅当已成功生成的视频明显短于本次录制经过时间时，复制所有编码轨道并为视频的最后一帧写入结束时间；不重新编码。新文件校验成功后才在同目录替换原文件，失败时保留原文件。设备上的视频副本验证保留了全部三个轨道的样本数据与时间戳，并将测试副本的时长修正为 5.4 秒；实际静止画面录制约 13.6 秒的视频也被媒体库识别为 13.6 秒，用户确认正常。该处理不能恢复系统未采集到的画面。
